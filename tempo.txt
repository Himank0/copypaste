CMD Walkthrough Context Dump

Meeting CMD walk through me Ange Howe ne CMD (Contract TV) application ka walkthrough diya. Attendees mainly development team aur business stakeholders the. Session ka objective tha application ka functional understanding dena, dealer onboarding process samjhana, task/document lifecycle explain karna aur future walkthroughs ke liye context create karna. Meeting transcribed thi.

1. CMD Ka Purpose

Ange ne explain kiya ki CMD primarily ek partner/dealer lifecycle database hai. Ye contract repository nahi hai aur approvals bhi is system ke bahar hote hain. System ka focus dealers, contracts, modules, documents, dates aur statuses ko track karna hai. Actual contract documents application ke andar repository ki tarah store nahi hote; application unki lifecycle state maintain karti hai.

2. User Access & Login

Application me administrator aur read-only users hote hain. Administrator onboarding manually manage hoti hai. Login ke baad home screen par recently accessed dealers dikhte hain taaki users quickly apne active work items open kar sakein. Password management bhi administrators ke through handle hota hai.

3. Search Capabilities

Application simple aur advanced dono search support karti hai.

Advanced search ke through users search kar sakte hain:

Dealer
Dealer Code
Premise Code
Documents
Task Definitions
Statuses
Assigned User
Business Unit
Dealer Categories

Search functionality ka purpose hai existing dealer records, tasks aur documents ko locate karna.

Dealer creation process system ke bahar approvals complete hone ke baad start hota hai.

Flow roughly:

    ↓

    ↓

Template me company information store hoti hai:

Postcode

Dealer shell create hone ke baad system dealer reference generate karta hai. Dealer codes, SD codes aur premise codes immediately available nahi hote; ye contract signing ke baad commissions team provide karti hai.

5. Validation Behaviour

Upload template me formatting validations hoti hain:

Date format
Alphanumeric format
Column mapping

Ange ne mention kiya ki system incorrect formatting reject karta hai, lekin business-value validation strong nahi dikhi. Example ke taur par past date bhi accept ho sakti hai agar date format valid ho. Mandatory vs optional fields meeting me fully clarify nahi hue.

6. Dealer → Task → Contract Relationship

Meeting ka ek major clarification ye tha ki CMD ka core model dealer, task aur contract ke around hai.

Relationship:

Dealer
   ↓
Task
   ↓
Contract / Documents / Modules


Ek dealer ke multiple tasks ho sakte hain.

Task represent kar sakta hai:

New onboarding
Contract renewal
Service change
Additional services

Task business process ka key driver hai aur uske andar documents aur modules define hote hain.

7. Task Creation

Task create karte waqt user:

Task Definition select karta hai
Applicable documents choose karta hai
Requester identify karta hai
Effective date set karta hai
Task assign karta hai

Requesters generally partner managers hote hain jinhone approval process initiate kiya hota hai. Unhe monitoring ke liye read-only visibility di ja sakti hai.

8. Duplicate Tasks

Ange ne bataya ki system duplicate task creation actively prevent nahi karta.

Consequences:

Duplicate documents create ho sakte hain
Cleanup manually karna pad sakta hai
Cancellation/termination required ho sakti hai

Ye future improvement area lag raha tha.
